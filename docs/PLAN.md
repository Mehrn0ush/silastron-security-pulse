# Plan: indexable dashboard, feeds, and malicious package pulse

Status: **proposal, awaiting approval**. No code is changed by this PR. Measurements
were taken on 2026-11-12. Source findings are in `docs/malware-source.md`.

## 1. What I found in this repo

- Site = `preview/` (static shell, `app.js` 2,659 lines) + `data/` copied from the
  `pulse-state` branch `published/` by `publish.yml` (Pages artifact). Collect never
  deploys; Publish is `workflow_run` of Collect (auto) or manual with `confirm=PUBLISH`.
- Home page content that is invisible without JavaScript today: status banner, data
  status, overview cards, "What's changed", "Recently added to CISA KEV" table. The
  `<noscript>` banner says nothing is shown.
- **Per-CVE static pages already exist** (`static_pages.py`): 1,773 pages plus home =
  1,774 URLs in `sitemap.xml`, no `lastmod`; `robots.txt` exists. Section A.3 therefore
  applies: they go in the sitemap (with real `lastmod`).
- Existing guarantees I will keep: strict CSP meta (`default-src 'none'`, no inline
  script), Collect/Publish split, fail-closed decisions, no composite score.
- **EPSS gating today**: the adapter is hard-disabled in code
  (`pipeline.py:223`: `collect_epss(..., enabled=False)`, `epss_enabled: False` in the
  summary); every record carries `unavailable_record`. It stays disabled pending
  redistribution clearance (`constants.py:61`, `docs/limitations.md`). Not changed.
- Published data volume is **already larger than the budget in the brief**:
  `pulse-state/published/` is **562 MB in 5,341 files** (snapshots/ 372 MB, `latest.json`
  63 MB, history/ 83 MB, cve/ 36 MB, `catalog-index.json` 7.8 MB). GitHub documents
  that published Pages sites may be no larger than 1 GB and deployments time out
  after 10 minutes.
- Tests: 346 unit tests plus Playwright (`tests/e2e`, fixture site built by `serve.py`).

## 5. Size estimates

Measured from the clone: 15.5 MB of name+id data in 3-character shard buckets, max
bucket 293 KB before versions and summaries; with versions, 200-char summaries and
origin, the lookup index is about 35 to 45 MB raw (about 6 to 9 MB gzipped on Pages,
which serves gzip). Shards are adaptive-prefix so none exceeds 500 KB; I expect 150 to
400 shards (prefix length chosen per ecosystem, recorded in `manifest.json`). Weekly
digests: 26 x (json + csv) with the heaviest week about 3,000 rows, under 1 MB each.
Pages: ~40 HTML files. Malware tree total estimate **about 50 MB raw**. Current site
562 MB, so about 610 MB afterwards, under the 1 GB Pages limit.

State storage and repo growth: raw upstream is never committed. Compact aggregates
(shards + weekly digests + `summary.json` + the upstream commit SHA) go to a new
orphan branch `malware-state`, only changed files per commit. Upstream adds roughly 1.5k
reports per month recently (about 18k/yr, 2025 was 193k); at about 150 B per record that
is 3 to 30 MB raw per year, about 1 to 8 MB packed. Cache-only state was rejected
(Actions caches evict and cannot be audited). A yearly squash of `malware-state` is
available if it grows.

## 6. Where I think the brief is wrong for this codebase

1. **The 300 MB site / 5 MB file budget cannot pass today.** The site is 562 MB and
   `latest.json` is 63 MB (3.9 MB gzipped), `catalog-index.json` 7.8 MB. Proposal: the
   CI check enforces 5 MB per file and 300 MB for everything under `/malware/` plus
   all new files, with an explicit allowlist for the two existing large files and a
   whole-site hard limit of 900 MB (Pages limit 1 GB). Reducing the 372 MB of
   `snapshots/` is a separate decision about the audit trail; **I need your call**
   (keep, or retain only the last N).
2. **"Schema validation of every record, failing closed" would block forever.**
   Upstream has quirks: 78 records without `published`, 8 empty ids, one record with no
   package name. Proposal: quarantine invalid records individually, list them in the
   run summary, and fail the run only if rejects exceed 0.1% of records or any known
   good record disappears. Records without `published` are in the lookup index but in no
   weekly count (their week is unknown; I will not guess).
3. **Spike rule (5x the 12-week median) misfires on tiny medians.** Most ecosystems have
   medians of 0 to 3 per week, so 10 reports would be a "spike". Proposal: label a
   spike only if count > 5x median AND count >= 50, with a documented floor.
4. **Methodology page for the KEV side: yes, separate.** "How to read these signals"
   plus provenance is about 90 lines; it moves to `/methodology/`, and the home keeps
   `#provenance` as a short summary and link, so existing links keep working.
5. **Where the malware collector commits.** The brief says commit with
   push-with-retry; here state lives on a state branch, so `malware-state` is the
   target (not `main`). `data/commentary/<week>.md` stays on `main` (hand-written).
6. **One deployment, two sources.** There is one Pages artifact and one `pages`
   concurrency group. Publish rebuilds the whole site from `pulse-state/published` and
   `malware-state`. Proposal: malware Collect never deploys; Publish gains a second
   `workflow_run` trigger on "Collect malware", and a KEV failure no longer stops the
   malware section from updating (and vice versa). Each side keeps its own
   last-good snapshot and its own "data stale since" notice. This touches `publish.yml`,
   so I want your approval of the approach before PR 4/5.
7. **Classification** is not available as a structured field upstream (only a CWE-506
   tag on 33,808 reports), so per C2 we show none. "Reporting origin" is
   `malicious-packages-origins[].source`, which upstream says has "little value to
   consumers"; shown as an origin label only.
8. **Daily increase flag**: history gives p99 750/day and max 76,855 (2025-11-11).
   Proposal: accept but flag any day over 2,000 new reports; the 2% drop gate counts
   withdrawn explicitly.
9. **Name normalisation** (documented rules I read): PyPI lowercases and collapses runs
   of `.`, `-`, `_` to `-` (PyPA name-normalization spec); npm new names must not
   contain uppercase (legacy uppercase exists, so fold to lowercase for lookup and keep
   the exact name for display); NuGet ids are case-insensitive; crates.io index file names
   are lowercase while fields are case-sensitive, so fold case; Packagist names must be
   lowercase; Go modules are case-sensitive (match exactly); Maven coordinates are
   `group:artifact` and exact. For RubyGems I found no documented case rule on the pages
   I read, so I will match exactly and will not fold; tests pin this.
10. **Atom and sitemap validation**: Atom via the vendored RFC 4287 schema as in pqc.
    Sitemap XSD (`sitemap.xsd`, `siteindex.xsd` are served by sitemaps.org) will be
    vendored; I will record its licence on vendoring.
